## 4. Blocking question (R-07): which backend do the module pages use?

The frontend's module screens (inventory, approvals, projects, pools, reservations, dispatch, alerts, incidents, metering, users, …) call about 60 API paths. **None exist in this repository's backend**, and several differ from the LLD catalogue (`/inventory/assets` vs `/assets`, `/workload-submissions` vs `/workloads`, `/users/{u}/role` vs `/admin/memberships`). The README points to an "integrated TeleScope API on :8000" in the *Quantum_Monitoring* monorepo.

RBAC for "all existing QRP modules" (master prompt §11) has to be enforced in whichever backend serves those modules. Options:

* **A — The real module API is in Quantum_Monitoring.** Share that repository; RBAC core is built here per the LLD and the same `TenantContext`/`Authorizer` contract is applied there (or the modules are moved here).
* **B — This repository's backend is the target.** RBAC (identity, roles, admin APIs, audit, frontend) is built fully now. Module endpoints are built per the repo's own plan (Phases 4–7: inventory, providers, approvals, quotas, reservations, dispatch, metering, SLA, support) with their permission guards from the first line. Frontend module pages are re-pointed to LLD paths as each module lands; until then they show an explicit "not available in this deployment" state, not fake data.
* **C — Both:** build RBAC here now (phases RBAC-2…6), decide module ownership before RBAC-7.

**Decision (05-Nov-2026): C.** RBAC-2…6 proceed in this repository; module ownership is decided before RBAC-7.

**Decision (06-Nov-2026): A.** The module endpoints are served by the TeleScope backend in the `Quantum_Monitoring` monorepo (`app/`). RBAC-7 applies the QRP contract there: session-only identity, deny-by-default, tenant isolation. First tranche (identity hardening + test-harness reconciliation) is complete; see the RBAC-7 change-log entry. Open sub-decision below (7c).

**Sub-decision (7c — role-model depth): resolved (i), 06-Nov-2026.** Kept TeleScope's role names and moved `approvals:decide`/`approvals:override` off the all-powerful admin onto the operational approver (`QuantumOpsAdmin`), matching QRP's SoD invariant. Governance tests now use an explicit `APPROVER` identity for decide/override/authorize while the platform admin retains read-only oversight. Original framing kept below for the record.

**Open sub-decision (7c — role-model depth) [resolved — see above]:** TeleScope has its own role set (legacy `Admin`/`Operator`/`Researcher` + extended `PlatformAdmin`/`SecurityAdmin`/`QuantumOpsAdmin`/… ) with an in-code permission map, where `Admin` holds every permission including `approvals:decide`. QRP's authoritative model has 9 system roles and a separation-of-duties invariant (**PLATFORM_ADMIN must NOT hold `approval:decide`**). Fully importing QRP's role model into TeleScope would change who can decide approvals and conflicts with the governance tests that use `Admin` as the decider. Options: **(i)** keep TeleScope's role names but align their permission *sets* and move `approvals:decide` off the all-powerful admin onto a dedicated approver role; **(ii)** remap TeleScope roles 1:1 onto QRP's 9 system roles (largest change); **(iii)** treat action-level SoD (submitter≠decider, already enforced and tested) as sufficient and leave the role→permission map as-is. Awaiting owner choice.
